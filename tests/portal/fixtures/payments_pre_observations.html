{% extends "portal/base.html" %} {% load i18n ptbr %}{% comment %} Cards rather than a table. A MEI owner opens this on a phone, and a five-column table on a 375px screen is either a horizontal scroll or four truncated columns; a card stacks. The obligation is named HERE rather than by the view, and that is a rule rather than a preference. A test greps every source file under apps/ for the quoted obligation code, so that the deadline engine stays driven by its seeded rule rows instead of a ladder of branches on the code -- and it cannot tell a display label apart from the branch it exists to prevent. The view hands down the raw code and this page decides what to call it, with the code itself as the fallback, so a type nobody has labelled yet renders as the string a Receita document already uses rather than as nothing. Nothing here reaches through a relation. Every value on a card is a scalar the view already read, because rendering happens inside the portal transaction and under app_portal -- a role holding SELECT on seven tables, and the type reference is not one of them. A page that followed the relation would not be slower; it would be permission denied on a screen a client had open. Standing is never carried by colour alone, and never by a word alone either. Each row states where it sits AND what that costs: "Em atraso" tells an owner the row is late, and only the sentence after it says the amount grows while they read. Every branch also ends on something the reader can DO -- ask for the guia, pay it, wait -- because a consequence with no next step leaves a person alarmed and stuck. The five words below are the only thing standing between this page and the raw column. `status` arrives as the stored value, and the client is never shown it: each branch maps one value onto a pt-BR word AND the sentence that says what it costs. A branch that fell through to the value itself would put an English enum on a MEI owner's phone, so there is no such fallback -- the last arm is the scheduled case by name in its copy, not a default that prints whatever arrived. Both dates are shown when they differ, and the note says WHY they differ rather than merely that they do. DAS-MEI rolls FORWARD off a non-business day, so without the explanation the resolved date looks like the rule's own and a client checking this screen against a Receita document sees two different days and nothing that tells her which one she has to pay by. DASN-SIMEI does NOT roll. It falls on 31 May and stays there even when that is a Saturday (Resolução CGSN nº 140/2018 art. 109, recorded in docs/regulatory-watch.md). That is why the roll note is reached through an `elif` behind the annual type rather than written beside it: a DASN row can never be handed the sentence saying its deadline moved, however the stored dates came to disagree.
