{% extends "allauth/layouts/entrance.html" %} {% load allauth i18n %}{% comment %} Confirming a fresh set of recovery codes — and, when a set already exists, confirming the destruction of the old one. The screen exists because the action is irreversible and one-click. Generating replaces every unused code the account still holds: a reader who has the old list on paper is holding paper that stops working the moment this form is submitted, and nothing after the fact can bring it back. So the warning names that consequence in the branch where it applies, and the submit carries the danger ramp there rather than the affirmative one, which would make destroying the old set look like agreeing to something. `unused_code_count` is what distinguishes the two cases and comes from the view's context. First-time generation is not destructive and reads as an ordinary confirmation. Upstream renders the form body with `form.as_p`. That writes its markup from Django's widget templates in site-packages, which Tailwind's `@source` does not scan and `tests/ui/templates_scan.py` does not walk, so anything it emitted would ship with no compiled rule and no guard watching. The form is walked through the fields element instead, which routes each control through this project's own partial and carries the announced summary with it — the same reasoning `templates/allauth/elements/fields.html` records.
