{% load i18n %}{% comment %} One form field -- label, control, help, error -- from context alone. Context: field -- a Django BoundField. Nothing else is read, and nothing is looked up. Why the markup is hand-written rather than `{{ field }}`: Django's own widget templates live in site-packages, which Tailwind's `@source` does not scan and `class_tokens()` does not walk. A class written there has no compiled rule and no test watching it, so the control would ship unstyled while every guard stayed green. Every class-bearing tag here is therefore emitted by this file. Why one tag rather than one branch per widget: `aria-invalid` and the `aria-describedby` chain are the whole point of the partial, and they are identical for an input, a select and a textarea. Repeating them per variant is how the three drift apart. So the branch chooses the opening tag and its type-specific attributes, then all the shared attributes -- name, id, class, required, and the two accessibility ones -- are written exactly once. The accessibility contract, in order of how quietly each fails: * `aria-describedby` names the help id, the error id, both (space separated), or the attribute is omitted. It is never emitted empty: an empty value points at no element, which reads to assistive technology as a broken reference. * `aria-invalid="true"` appears only while the field has errors. The clean state omits it rather than saying "false", because `.field-input[aria-invalid="true"]` is what draws the error border -- and a literal "false" would also make every untouched field on a fresh form announce a validity state nobody asked about. * The label is always rendered and always visible, with `for` bound to the same id the control carries. A placeholder is not a label; it disappears on first keystroke, which is when a person most needs to re-read it. A password value is never echoed back into the markup, and neither is a file input's -- the browser rejects the second and the first is a credential in a page cache.
